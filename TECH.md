# Tech Stack — QuizMaster

## Frontend

| Компонент | Технологія |
|---|---|
| Мова програмування | JavaScript |
| Фреймворк | Vanilla JavaScript (без фреймворку) |
| Керування станом | JavaScript-змінні та ES Modules |
| Маршрутизація | Навігація між HTML-сторінками |
| Стилізація | HTML5 + CSS3 |
| Збірка | Vite |

## Чому обрали:

Для розробки frontend-частини QuizMaster обрано HTML5, CSS3 та Vanilla JavaScript, оскільки вони дозволяють створити інтерактивний вебзастосунок без використання додаткових фреймворків. Це дає змогу зосередитися на реалізації основного функціоналу: створенні та проходженні вікторин, роботі з формами, відображенні результатів і взаємодії з backend API.

Для організації розробки обрано Vite, оскільки він забезпечує швидкий запуск локального сервера, підтримує JavaScript-модулі та дозволяє створювати оптимізовану збірку застосунку.

Такий набір технологій відповідає потребам навчального проєкту, спрощує початкове налаштування та дозволяє команді поступово розширювати функціональність QuizMaster.

## Backend

| Параметр | Значення |
|---|---|
| Мова програмування | Python |
| Фреймворк | FastAPI |
| База даних | PostgreSQL |
| ORM / драйвер | SQLAlchemy (ORM, sync) + Alembic (міграції), psycopg |
| Автентифікація | JWT у httpOnly cookie (PyJWT), хешування паролів argon2 (argon2-cffi) |
| Документація API | OpenAPI / Swagger UI |

**Чому обрали:** 

1. **Python + FastAPI:** вибір мови та фреймворку обґрунтований переважно попереднім досвідом команди
2. **PostgreSQL:** архітектура проєкту потребує реляційної бази даних. Тут є зв'язки «один до багатьох» (наприклад, один тест має багато питань) і «багато до багатьох» (кожен користувач може проходити декілька тестів, і кожен тест може проходитися декількома користувачами). Окрім того, PostgreSQL добре інтегрується з SQLAlchemy та Alembic
3. **SQLAlchemy (sync) + Alembic, psycopg 3:** обрано синхронний підхід, оскільки він простіший і легше піддається покриттю тестами. Проєкт має навчальний характер, тому великого навантаження на БД не очікується, а отже, значущої різниці порівняно з асинхронним підходом не буде
4. **JWT у httpOnly cookie, argon2:** ТЗ прямо вимагає: «Токен передається клієнту через httpOnly cookie. Всі захищені кінцеві точки (endpoint) читають токен з cookie, не з Authorization header». Argon2 є одним із найсучасніших алгоритмів хешування паролів і рекомендується OWASP
5. **OpenAPI / Swagger UI:** FastAPI автоматично генерує OpenAPI-документацію, а Swagger UI доступний за адресою /docs

## Інфраструктура

| Параметр | Значення |
|---|---|
| Хостинг frontend | Vercel |
| Хостинг backend | Render |
| Хмарне сховище | Не планується на початковому етапі |

**Чому обрали:** Vercel підходить для розміщення frontend на Vite, а Render підтримує backend на Python і FastAPI.

## Знання команди

**Що знаємо добре:** Основи програмування, HTML, CSS, JavaScript, Python, робота з Git та GitHub, базові принципи frontend і backend-розробки.

**Що вчимо по ходу:** Організація взаємодії frontend і backend, реалізація системи вікторин та робота над спільним командним проєктом.

**Як закриємо прогалини:** Спільне навчання, документація, Code Review та взаємодопомога.

## Прийняті технічні рішення

Для frontend обрано HTML5, CSS3 та Vanilla JavaScript із використанням Vite для організації розробки та збірки проєкту.
Для backend обрано Python і FastAPI, базу даних PostgreSQL та SQLAlchemy для роботи з даними.
Основні технології узгоджені командою з урахуванням вимог QuizMaster, досвіду учасників та можливості подальшого розвитку застосунку.
Для розміщення frontend обрано Vercel, а для backend обрано Render.
